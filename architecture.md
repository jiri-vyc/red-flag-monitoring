## Domain

```
Regulation → Internal policy → Rule → Rule version
Client → Transaction → Transaction evaluation → 1..N rule evaluations → AML event
```

Alerts (issue #13, [V18–V20](spec/datovy-model.md#rozhodnutí-vyhodnocení)): after a run's transactions are stored, its hits are grouped into `aml_events` by the rule's `alert_granularity`: one event per hit transaction (`transaction`, rule B) or per client and calendar month (`client_month`, rules A and C). `aml_event_hits` links every hit to exactly one event. The `alert_id` is readable and unique within the run (`R-02-TX000012345`, `R-01-K000123-2026-07`). An event is a decision aid, not an AML determination.

Triage (issue #14, [V21–V24](spec/datovy-model.md#rozhodnutí-vyhodnocení)): once the events are stored, the run proposes a deterministic triage for every alert (`aml_event_triages`, `source = rules`): priority 0–100 from table P of SVZ-03 with the factor breakdown, `FP` / `REVIEW` and a reason, built by the pure `domain/alertTriage.ts`. `POST /api/evaluation-runs/:runId/triage` asks Claude on Bedrock for a second proposal (`source = llm`), one call per client with all its alerts in the run ("see the whole story"), highest priority first. The model sees precomputed factors and a sample of hit transactions, decides `FP` / `REVIEW` and writes the reason; it never changes the priority. Guardrails turn a model `FP` into `REVIEW` for scenarios the policy reserves for a human, PEP clients and high-risk jurisdictions. Prompt, response, model and tokens are stored in `alert_triage_llm_calls`. The mandatory FINREG CSV comes from `GET /api/evaluation-runs/:runId/aml-events.csv`.

Relations (data model M3 to M5): a policy cites 0..N regulations through its legal bases, each with an optional provision `ref` (a purely internal policy cites none). A rule may have no policy. Each rule version has its own 1..N legal bases (regulation + required `ref`), not inherited from the policy. The web shows the legal basis of the running version, else of the newest one (`findRuleLegalBases`), and derives a regulation's related policies and rules from these legal bases. The live adapters map backend regulation wordings (`regulationVersionId`) to regulations, and a new manual rule cites the newest wording.

Users and roles (issue #6): a user holds one or more of `compliance_analyst`, `compliance_officer`, `lawyer`, `contact_person` (AML zákon § 22) and `designated_person` (§ 22a). Each rule version names the role its hits are escalated to (`escalationRole`, default `contact_person`). The web sets it at version creation (manual rule form, new version editor) and in the draft edit, which saves content and config of an unreviewed version in place. While a draft can't be edited in place (`rules.canEditDraftContent` false, live until issue #8), the rule detail offers the role at review and sends it with approve or reject; otherwise the review sends `null`, which keeps the version's role. Run results read with `?role=` show only the hits escalated to that role. There is no auth: the web picks the user and active role, the backend trusts it and checks no permissions.

Rule statuses: `draft`, `pending_for_review`, `update_for_review`, `active`, `inactive`. A rule returns a score of 0–100 and a trace. The adjusted score is `score × sensitivity / 100`. Each rule version holds its content (code + Czech explanation, or agentic rule text) and its config (sensitivity, risk profiles). Any edit of content or config creates a new version that goes to review (data model M7). Evaluation always uses the running approved version, never a pending one. The client whitelist is not versioned: it lives at rule level as rule × client entries with a required reason (M16), and changes apply immediately without review. Regulatory-mandatory rules have `whitelistAllowed = false`. Each batch snapshots the whitelist together with the rule versions, so past batches stay reproducible. Whitelist approval and periodic review (CNB benchmark 2/2023) are not in the MVP and need compliance review.

## Evaluation engine (`src/backend`)

`POST /api/evaluation-runs` → `EvaluationRunUseCases.startRun` fixes the active deterministic rule versions and the latest reference lists, stores the run as `running` and hands it to an `EvaluationRunLauncher` (in the API process locally, a Lambda worker when `EVALUATION_WORKER_FUNCTION` is set). `EvaluationRunExecutor` loads clients, transactions and ČNB rates once (D18), evaluates the transactions in scope with the pure `domain/transactionEvaluator.ts` and stores them in batches of 1,000 with progress counters. Only rule results other than `pass` are stored (V16). It then loads the run's stored hits, groups them with the pure `domain/amlEvent.ts` (`groupRuleHitsIntoAmlEvents`), writes the AML events through `AmlEventRepository` in one transaction and stores their rule-based triage (`AlertTriageUseCases.triageRunWithRules`, ~6 s for 10.8k alerts) before it marks the run `completed`. Runs are read through `EvaluationRunQueries`, their AML events through `AmlEventQueries`.

## Drafting jobs (`src/backend`)

The wizard's LLM steps run as `drafting_jobs` rows ([spec/drafting-jobs.md](spec/drafting-jobs.md)). `POST /api/drafting-jobs` → `DraftingJobUseCases.startPolicyJob` stores pasted text as a regulation version, inserts a `pending` `policy_from_regulation` job and hands it to a `DraftingJobLauncher` (in the API process locally, the `rfm-drafting-worker` Lambda when `DRAFTING_WORKER_FUNCTION` is set). Approving a policy version stores a `rules_from_policy` job in the same transaction as the review. `DraftingJobExecutor` claims the job (`pending` → `running`, so a repeated invocation is a no-op), fetches a URL source when needed, calls the `DraftGenerator` port (`BedrockDraftGenerator` with `DRAFT_GENERATOR=bedrock`, as on the deployed worker; `DummyDraftGenerator` otherwise) and writes the drafts together with `succeeded` in one transaction. Failures end as `failed` with the error; an unfinished job older than 16 minutes is reported as `failed`. The web polls jobs every 5 s while one is in flight.

## Audit log (`src/backend`)

Issue #5, logs only: every change of state and every LLM call writes one `[audit] action=… entity_type=… entity_id=… actor_id=… payload={…} [/audit]` line through `application/audit/auditLog.ts` (`recordAuditEvent`) after the change succeeded. Covered: regulation, policy, rule and reference list creation and versions, version submission and review, rule enable/disable/active version, whitelist add/remove (with the removed entry), evaluation run start/completion/failure, drafting job creation/start/success/failure, rule-based and LLM triage proposals, and every Bedrock call (`llm_call.completed`: model, tokens, duration, SHA-256 of prompts and response; the texts themselves stay in the database). The lines land in `/aws/lambda/web/rfm-api` and `/aws/lambda/rfm-drafting-worker`, kept 10 years, and the saved Logs Insights query `rfm/audit` parses both. Best effort: not part of the database transaction, the actor comes from the request body, and enabling a rule or removing a whitelist entry has no actor yet.

## Rule gap review (`src/backend`, iteration 1, local only)

A triggered job that finds rule thresholds clients stay just under and behaviour no rule covers ([spec/rule-gap-hunting.md](spec/rule-gap-hunting.md)). Its findings are ruleset artefacts with the affected clients for research. It never creates alerts, writes no table and changes no rule version.

- **Flow:** `POST /api/rule-reviews` → `RuleReviewUseCases.startReview` (409 while one runs) stores a `running` report document and hands it to `InProcessRuleReviewLauncher`. `RuleReviewExecutor` loads the active rule set (or an evaluation run's fixed versions) and the dataset once, then runs the stages in `RuleReviewAnalysis`: one baseline pass with the production `evaluateTransaction`, sweeps of the DSL constants from the `pass` traces, a re-run per feature parameter step, association and the SVZ-03 čl. 7 coverage matrix. It rewrites the report with progress and ends `completed` or `failed`. A report still `running` after 20 minutes is shown as failed.
- **Pure core:** `domain/ruleReview/`: relaxable parameters with the caps per type, the growth cap, repetition, trace margins, association, coverage matrix, backtest of a DSL definition, the perturbation test. Long stages are generators that yield every 5,000 transactions, so the API keeps answering while a review runs.
- **Feature parameters:** pattern features read their thresholds from `FeatureContext.parameters` (`domain/features/featureParameters.ts`), by default the values of `thresholds.ts`. Detection always runs with the defaults; only the review relaxes them. `detectionRegression.test.ts` pins per-rule hits on the full dataset and the features of a fixed sample.
- **Store:** `FileSystemRuleReviewReportStore` writes one JSON per review to `RULE_REVIEW_DIR` (default `src/backend/.rule-reviews/`, git-ignored). Finished reports are immutable. Not usable on Lambda; iteration 2 picks S3 or tables.
- **LLM ports:** `FindingExplainer` and `HypothesisExplorer` are no-ops unless `RULE_REVIEW_LLM=bedrock` (adapters from step 1b, not wired yet). The executor backtests every hypothesis itself, enforces the tool call budget and never lets a Bedrock failure fail the review.
- **CLI:** `npm run rule-review` runs the same review and writes the report; `-- --probe` prints the sensitivity and association tables with FX conversion and with volume read as CZK.

## Web (`src/web`)

Our team owns the frontend only. The backend is someone else's, and the web adapts to its API.

```
app/ (thin route pages)
  → features/<f>/components (screens)
    → features/<f>/api/hooks.ts (React Query, registers service usage)
      → service.ts: resolveService(name, { mock, live })
          → live.ts: fetch relative /api/... → Next rewrite → BACKEND_URL; responses validated with Zod
          → mocks/services/<f>.mock.ts: localStorage store (mocks/store), seed (mocks/seed)
```

- **Features:** `dashboard`, `regulations`, `policies`, `rules` (incl. `domain/ruleLifecycle.ts`, the pure state machine for statuses and versions), `batches` (CSV upload, OK / TO CHECK / ALERT buckets, transaction detail), `transactions` (client transactions), `fauReports` (FAÚ report drafts from an alert, mock only), `wizard` (regulation source → policy draft → rules → review).
- **Evaluation run start and polling:** "Run evaluation" sends `POST /api/evaluation-runs` (optional scope: limit, from, to) and opens the run detail. `useBatch` and `useBatches` poll with React Query `refetchInterval` (2 s live, 400 ms mock) while a run is `processing` (`importing` or `running`) and stop once it is `completed` or `failed`. They also stop when the run's counts stay unchanged for 5 minutes (`STALLED_RUN_LIMIT_MS`) and show it as not responding with a "Check again" button that resumes polling; the status stays with the backend. The progress view's ETA uses the rate between consecutive polls (`dataUpdatedAt`), smoothed with an exponential moving average, and counts down between polls.
- **Gap analysis:** the Rules page has a "Gap analysis" button gated by `canManageRules` (the compliance officer; other roles see it disabled with a role hint). `/rules/gap-analysis` (`features/ruleReviews`) starts a review, polls it every 2 s while `running`, lists past reviews and shows the coverage matrix, the gaps, the recalibration candidates, the association groups and the Bedrock explanations and rule hypotheses, with links to the client's transactions. The service follows the `rules` data source; the mock serves a report from a local run (`mocks/seed/ruleReviewReport.json`).
- **Users and roles (issue #6):** `features/users` (service `users`, `GET /api/users`). `config/currentUser.ts` holds the user and active role picked in the sidebar (`CurrentUserPicker`, kept in `localStorage`); `useRolePermissions` hides actions the active role may not take. Batch queries send `?role=` and key on it, so switching the role refetches.
- **Client transactions (issue #9):** `features/transactions` (service `transactions`, `GET /api/transactions`) at `/transactions`, not in the sidebar menu (reached from the transaction detail). The client filter, the highlighted transaction and the return path live in the URL (`transactionsPath`). A failed rule card in the transaction detail links there with the client and the evaluated transaction; the list loads pages until that transaction shows and scrolls to it.
- **FAÚ report, OPO (issue #20, mock only):** `features/fauReports` (service `fauReports`) at `/fau-reports/[reportId]`, not in the sidebar menu. A transaction detail with bucket `alert` shows "Prepare FAÚ report" (`FauReportAlertAction`), or, once the alert has a report, a link to it with its status; roles without `canViewFauReports` (only the AML compliance officer and the contact person have it, § 38) see only that a report exists. The mock keys a report by batch and transaction; the backend will key it by the AML event id (#13), one active report per event. The draft follows MP FAÚ č. 4 sections I to VI: OPO number (`OPO-<year>-<NNNN>`), a fictional reporting institution (`reportingInstitution.ts`), the pseudonymous client, report type, a section V text from a deterministic template (`domain/fauReportDraft.ts`: triggering transaction, failed rules with met trace steps, adjusted score and the evaluated version's legal bases) and execution (§ 15, § 20). Identification fields (name, birth number, ID document, address) are never stored: they are disabled empty inputs marked "Complete from KYC before filing". Workflow in `domain/fauReportLifecycle.ts`: `draft` → `pending_approval` → `approved` → `submitted`, a rejection returns to `draft` with a required reason, edits only in `draft`, the approver must not be the author, "Mark as submitted" needs the channel and the FAÚ reference number. Permissions `canPrepareFauReport` (contact person) and `canApproveFauReport` (compliance officer). Deadlines (`domain/fauReportDeadlines.ts`): 2 working days from the report's creation (suspicion conclusion, SVZ-03 čl. 8.8) and under 5 calendar days from the alert (MP FAÚ č. 4); the alert time is the run's `finishedAt` (or `uploadedAt`), weekends are skipped, holidays are not. "Download draft (Markdown)" builds the file in the browser (`domain/fauReportMarkdown.ts`, always Czech). The history is a simple list in the mock; the backend timeline will come from `audit_events` (#5). Template, prefill and workflow need compliance review.
- **Deleting rules, policies and regulations:** the detail screens offer a delete (`DeleteRuleAction`, `DeletePolicyAction`, `DeleteRegulationAction` on the shared `components/ui/DeleteConfirmation.tsx`: inline confirmation, then back to the list) only when a pure domain check allows it; otherwise the button is disabled with the reason. A rule must never have had an approved version (`canDeleteRule`, it may have been used in an evaluation), a policy must never have been approved and have no derived rules (`findPolicyDeletionBlocker`), a regulation must not be cited by any policy or rule version (`findRegulationDeletionBlocker`). Gated by `rules.canDeleteRule`, `policies.canDeletePolicy` and `regulations.canDeleteRegulation`: the mock deletes, the live API has no endpoints yet (BE-21 to BE-23, issue #30).
- **Policy and regulation links:** `PolicyLink` and `RegulationLink` (rules list, rule detail, legal bases) take the name from a cheap name index (`usePolicyNames` / `useRegulationNames`, one `GET /api/internal-policies` / `GET /api/regulations` each, no versions), not from the full lists, and fall back to the ID while it loads or when the name is unknown.
- **Current policy version (BE-11):** the live adapter takes a policy's status, text, legal bases and approval from the latest version, unless that one is rejected (or superseded): then from the latest approved version, which stays in force. One rule (`findCurrentVersion` in `features/policies/domain/currentVersion.ts`) serves both the live adapter (DTOs) and the detail screen, which shows that version as current; the version history keeps every version.
- **Policy text editing and version diff (issue #28, web only):** the draft editor in the policy detail and the policy step of the wizard share `PolicyTextField` (`features/policies/components`), an "Edit / Preview" toggle that renders the current, unsaved text through `MarkdownText`; the text stays in the parent, so edits survive the switch. Approved drafts in the wizard show the formatted text read-only. With at least two versions, "Compare versions" in the version history shows a line diff of any two versions (`diffLines` in `features/policies/domain/lineDiff.ts`, LCS-based), marked with +/−, `<ins>`/`<del>` and hidden "Added"/"Removed" labels, not by colour alone.
- **Policy selection in the wizard (issue #28):** each not yet approved draft in the policy step has a checkbox (checked by default). "Approve policies and generate rules" approves only the checked ones (`findPoliciesToApprove` in `features/wizard/policySelection.ts`); skipped drafts stay drafts and can be edited, approved or deleted later in the policy detail. The rules, review and done steps get only the approved policies (`keepApprovedPolicies`). The button is disabled while nothing is checked and nothing was approved in an earlier attempt. A resumed run with skipped drafts reopens the policy step (it cannot be told apart from an interrupted approval); continuing there with nothing checked goes on with the approved policies. Rejecting a policy draft needs the backend (BE-11) and is not offered.
- **Backend errors:** `lib/httpClient.ts` turns non-2xx responses into `ApiError`. The message carries the backend `error` and, for a 400 from request validation, its zod `issues` as `field.path: message`, so `ErrorState` and mutation errors show which field is wrong.
- **Mode selection:** `config/apiMode.ts`. `NEXT_PUBLIC_API_MODE` sets the global default (`mock`), and `NEXT_PUBLIC_API_MODE_<SVC>` overrides it per service. Live mode never falls back to mocks.
- **Mock-only code:** everything lives in `mocks/`, including the browser evaluation engine (`mocks/evaluation`) and the generation templates (`mocks/generation`).
- **i18n:** `i18n/en.ts` and `i18n/cs.ts` are typed dictionaries. The locale is stored in a cookie and read in the root layout, so the server and client render the same text. Only UI strings are translated, not data.
- **Env:** `config/env.client.ts` holds `NEXT_PUBLIC_*` only. `config/env.server.ts` holds `server-only` values (`BACKEND_URL`). Secrets go in Vercel env vars, never in `NEXT_PUBLIC_*`.
- **Styling:** CSS Modules plus tokens in `app/globals.css`. The UI is light only. The root font size is fluid (`clamp`) so the app is readable on a projector. Runtime dependencies are `lucide-react`, `@tanstack/react-query` and `zod`.

## Next-step features

These features are built in the web and work on the mock data: switch "Data source" in the menu footer to **Mock** to try them. They are the next steps of the product: each one waits only for the backend endpoint in the last column, and the web turns it on in live mode once the endpoint exists.

Each section runs either fully live or fully on the mock. What the live API cannot do yet, the web hides in live mode. This is driven by `capabilities` in the service contract (`features/*/api/contract.ts`); the UI reads them through hooks (`useBatchesCapabilities`, `useRulesCapabilities`, `usePoliciesCapabilities`, `useRegulationsCapabilities`, `useWizardCapabilities`, `useFauReportsCapabilities`), never by mode. The mock has everything `true`. Hidden code stays, and live adapter methods for unsupported operations still throw `unsupported` as a safety net. A section on the mock has a blue dot in the menu. The "Data source: Mock / Live" switch in the menu footer switches the whole web at runtime (remembered in the browser; env sets only the default).

The web labels the output as AI-drafted.
